# Attended CRM operational setup

CRM is the primary working record. The historical CRM master spreadsheet is an archive, never a continuing source of current owners, stages or consent.

The production-only `/api/admin/twenty-crm` operator uses the existing environment-superadmin and cross-site guard. Enable it explicitly with `TWENTY_CRM_OPERATOR_ENABLED=true` for an attended deployment and disable it again afterwards. It never runs in a build, on GET, in preview or in development, and it never sends mail, charges, deletes, merges identities or grants integration permissions. It is independent of the commerce operator.

1. `inspect` reads metadata and accessible records. Responses contain field definitions, counts and source-detail key names, not raw personal submissions. Refused optional objects remain refused.
2. `backup` captures metadata and records into an immutable gzip object under the existing private object bucket's `private/crm-operations/` prefix. Required People, Companies and source backups must all succeed. Readback verifies the actual compressed bytes with SHA-256 before it reports success.
3. `schema` requires a verified backup less than 24 hours old. It validates all existing field types before writing, adds missing fields only, and never rewrites existing definitions, option values, native stages or records. Replaying setup produces zero new fields.
4. `enrich` resolves the existing source groups, creates only the missing licence/project group definitions, and fills at most 50 records per attended request. Each batch saves and verifies a private journal first, rechecks target values before PATCH, and reads back the changed record while checking that all unrelated fields stayed the same. Existing manual groups, qualification and historical blocks win. Historic Meta answers are read from preserved CRM source records, never reimported from the old spreadsheet. Only explicitly identified reserved-domain tests and known System-created demo deals are marked; nothing is deleted.
5. `export` displays the selected private backup as gzip/base64 behind the same superadmin guard, for an explicit local copy. Backup keys are strictly confined to this operator's namespace.

The new `ptbk*` fields separate operational qualification from immutable historical answers and distinguish confirmed partners from candidates. Empty fields stay unknown. A past workshop or advertisement response does not become a new current enquiry, customer or partner. Neither product terms nor marketing choices are inferred.

Backups preserve the original metadata and records for manual recovery. Do not delete newly added fields as a casual rollback once the team has started using them. Restore only explicitly selected original values, keeping newer activity and imported source identities. No automatic destructive rollback endpoint exists.

After readback, set production `TWENTY_CONTACT_SOURCE_GROUPS` to the verified category-to-UUID map returned by enrichment. The existing self relation is `nadrazenyZdrojId`; primary source writes stay unchanged and only an empty parent is filled afterwards. Set `TWENTY_CRM_OPERATIONAL_FROM` to the activation instant only after field setup. Later website submissions with recorded `purpose=request` may initialize an empty relationship stage as a new enquiry; participation, newsletters, missing evidence and pre-activation enquiries never do. A confirmed paid Promptbook source may initialize an empty customer stage. Human-owned names, qualification, agendas, consent and existing stages are preserved. Optional grouping/projection failures are logged with redacted codes without failing primary contact delivery. Unknown types and invalid optional group configuration retain the original import behavior. Unassigned sources remain discoverable in the root view for review.

Open `/admin/twenty-crm` as the environment owner to enter the attended forms from the same origin. Do not bypass the cross-site guard for direct navigations to API routes.

`health` is read-only: it checks the two primary CRM objects, reports durable delivery/review/retry counts, and checks whether the latest eligible web Contact has its stable source key in CRM. `sync` explicitly invokes the existing regular contact worker with its existing lock, cutover and retries. It does not invent a test lead or run the independent commerce import. A busy worker or failed delivery is reported separately from success. Keep the normal scheduled route and source write paths unchanged.
