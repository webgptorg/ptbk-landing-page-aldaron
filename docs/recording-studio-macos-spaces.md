# Recording studio: macOS Spaces capture investigation

**Investigation date:** 2026-09-27  
**Result:** the web app has no supported way to enumerate native windows or make a missing window appear in the browser/OS chooser. The owner reported one Chrome-on-macOS case, but the exact versions, permissions and post-switch frame behavior are unknown, so this investigation does not attribute that result to every Mac or browser. The studio now exposes a plain `getDisplayMedia({ video: true, audio: false })` diagnostic and treats a muted required video track as an interruption. No end-to-end Space-switch workaround has been verified because this workspace has no physical Mac.

## Current studio behavior

The shared acquisition path is `components/recording-studio/RecordingSourcePicker.tsx` → `useRecordingStudio.ts` → `lib/recording-studio/recordingStudioDevices.ts`. A display source calls `navigator.mediaDevices.getDisplayMedia()` from the explicit Connect action. It requests ideal 1920×1080/30 fps capture quality, the selected optional `displaySurface` preference when `getSupportedConstraints()` reports support, and the user's sound choice. The source picker also calls `enumerateDevices()` to populate camera and microphone controls; that API does not enumerate system windows or display surfaces. The display path does not name or filter windows, identify Spaces, or pick a particular system window. The `window` value only asks for a preferred surface type; it does not select a window. Screen/tab/window choices remain in the browser or operating-system chooser.

Saved and historical source configurations contain a kind and, when available, a prior track label. They do not contain a live stream, window ID, or permission. Reconnecting after reload, stopping and starting a new take, or using a historical recording opens the chooser again. A canceled request leaves its configuration in place.

The ideal width, height and frame rate request capture quality after selection; the Screen Capture API does not let these options restrict the system choices. `displaySurface` requests a preferred pane only. The studio feature-detects support for that optional hint and does not enumerate or select display sources. The plain diagnostic deliberately removes both the quality request and hint to compare the standard browser path on the affected Mac.

Previously, a required video track was considered ready while its `readyState` was `live`, even if the browser had temporarily muted it. The studio now marks a muted required track temporarily unavailable, blocks Start, and interrupts an active take with an `interrupted` result and an actionable reconnect message. The finalized prefix remains available. This is explicitly not treated as an intentional pause. A track that ends is reported as ended/disconnected. A browser which freezes pixels without muting or ending its track cannot be identified from track state alone; visually confirm changing content in the preview.

## Evidence and boundaries

- Sources below were checked on **2026-09-27**. Mozilla's [Bugzilla 1772233](https://bugzilla.mozilla.org/show_bug.cgi?id=1772233) documents a distinct macOS Screen Recording permission failure: Firefox 128 on macOS 13 could list a window yet fail to capture it when permission was missing, and QA verified the permission-check fix in Firefox 129.0b2/Nightly 130 on macOS 13. This confirms permission state must be recorded separately; it does not describe another-Space visibility and is not evidence of a current Firefox Spaces bug.
- The [W3C Screen Capture specification](https://www.w3.org/TR/screen-capture/) says `displaySurface` may influence how source choices are presented, while the user agent still presents the choice. It explicitly leaves what counts as an inaccessible surface to the user agent/operating system. Examples include a window becoming minimized; temporary inaccessibility mutes the track, and permanent inaccessibility ends it. The specification does not say whether a window on another macOS Space is listed or keeps updating after a Space switch.
- [MDN's `getDisplayMedia()` documentation](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia), last modified 2026-09-07, says source permission cannot be persisted and options cannot restrict the user's choices. The new diagnostic uses only `{ video: true, audio: false }`, with no studio quality or surface hint.
- [Chrome's screen-sharing controls documentation](https://developer.chrome.com/docs/web-platform/screen-sharing-controls) says `displaySurface: "window"` preselects the Window pane, not a particular window. `surfaceSwitching` concerns switching browser tabs, not switching native app windows between Spaces; it does not solve the reported VS Code workflow.
- Apple's current [Spaces guide](https://support.apple.com/guide/mac-help/mh14112/mac) describes ordinary and fullscreen Spaces and app assignment to a desktop or display. Apple's [ScreenCaptureKit sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) documents a native Mac-app capture API, including the option to request on-screen windows; it is not a web API the studio can call to replace browser consent or its picker.
- Apple's [shareable-content API](https://developer.apple.com/documentation/screencapturekit/scshareablecontent/getexcludingdesktopwindows%28_%3Aonscreenwindowsonly%3Acompletionhandler%3A) distinguishes requesting only on-screen windows. This describes a native API parameter, not what Chrome, Firefox or Safari will list for another Space.
- Apple's [screen and system audio permission guide](https://support.apple.com/en-us/guide/mac-help/mchld6aa7d23/mac) identifies **System Settings → Privacy & Security → Screen & System Audio Recording** as the user-controlled permission list. The probe asks the tester to record that setting; it does not infer or change permission state.
- The [Chromium issue 546639189](https://issues.chromium.org/issues/546639189), filed 2026-08-15 and checked 2026-09-27, reports Chrome 151.0.7922.138 on macOS 26.5.2 timing out when starting selected Window or Entire Screen capture while Chrome Tab capture worked. A maintainer reported success on 2026-08-17 and closed it as **Won't Fix (Not Reproducible)** on 2026-08-21. It concerns capture startup, not a missing window or frames freezing after Space changes; it is not evidence of the owner's specific issue.
- Mozilla's [macOS 15 screen-sharing note](https://support.mozilla.org/en-US/kb/screen-sharing-warning-macos-15-sequoia), updated 2024-11-03, says Firefox 132 introduced the newer screen-capture API path after older versions triggered a macOS warning. It is not a report about Spaces behavior.
- A 2022 [WebKit report](https://bugs.webkit.org/show_bug.cgi?id=235469) describes old Safari 15 behavior on macOS 10.15 with multiple monitors. It is historical evidence only and is not used as proof of current Safari behavior. Likewise, unrelated fixed WebKit chooser bugs are not evidence that this report is fixed or still present.

No current primary browser/OS source located for this investigation specifies the availability or frame-update behavior of a window across macOS Spaces. The owner report does not include enough version or permission detail to attribute the missing entry specifically to Chrome or macOS. `getDisplayMedia()` does not expose a web API to enumerate those system windows or bypass the chooser. Apple's ScreenCaptureKit APIs document a native-app route; adopting a native helper would be a separate product option and is not a web-app fix here.

## Repeat the test on the affected Mac

Open `/admin/recording-studio/capture-probe` while signed in. This page requests only `getDisplayMedia({ video: true, audio: false })`, displays the returned track's surface/settings and frame callbacks, records mute/unmute/end timestamps, and lets the tester record the exact macOS build, browser version, permission state, window arrangement, chooser result, and observed continuity. It does not enumerate system sources, upload or save media, or keep the stream after the page is closed. The counter shows frames reported by the browser; to verify actual content updates, make a visible edit in VS Code and confirm that exact change appears in the preview after returning from another Space.

Run a short test for each row in the matrix, and repeat using the studio with **Bez preference** and, where useful, **Okno**. Record whether the VS Code window was visible and selectable, then whether changed content appeared after switching Spaces. Keep minimized, fullscreen, hidden, and different-monitor cases separate. Check macOS **Privacy & Security → Screen & System Audio Recording** manually; browser APIs do not provide a portable, reliable report of this setting. Export the diagnostic's copyable report before stopping the test stream.

## User-facing guidance and current workaround status

The source picker and restored screen-source cards link to the diagnostic and show the specific owner report without generalizing it to every Mac or browser. The UI labels trying the same ordinary Space first as a low-exposure experiment, not as a confirmed fix. It also explains that a full-display choice can include every window, notification, and other content that appears on that monitor. The owner's report says whole-display capture was selectable; continuous capture through Space changes is still unverified, so it is not called a tested workaround. The UI asks the operator to check the preview before relying on it and never switches automatically to full-display sharing.

No alternate browser or window-moving workflow is called a verified solution yet. A saved configuration restores preferences only; it cannot restore a prior window stream. Each explicit reconnect remains subject to the browser/OS chooser and permission confirmation. The physical Mac test remains outstanding; use the diagnostic report before presenting same-Space selection, moving the window after selection, whole-display capture, or another browser as a working Space-switch solution.

## Automated validation scope

The recording-studio end-to-end suite uses synthetic screen/tab/window streams; it verifies acquisition options, cancellation/retry, readiness, recording, storage, and exports, but does not open a native picker or reproduce macOS Spaces. Unit coverage also checks all three `displaySurface` hints (`browser`/tab, `window`, `monitor`/screen) and the fallback when optional supported-constraints detection is unavailable. Existing Windows runs recorded in `changelog/_current-preversion.md` used Windows 10 Pro 22H2 with Playwright Chromium 151.0.7922.34 and Edge 154.0.4258.37; screen capture was mocked there as well. This investigation therefore makes no claim of physical Windows, Safari, Firefox, or macOS picker compatibility. The plain diagnostic is available to collect such results on real devices.
